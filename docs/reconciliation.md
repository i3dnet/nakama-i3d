# Session reconciliation

Reconciliation starts after Nakama initializes the adapter and runs immediately, then every I3D_RECONCILE_INTERVAL (default 1m). Each pass has I3D_RECONCILE_TIMEOUT (30s). Startup failures are logged and retried on the next interval. Shutdown cancels the worker and stops its ticker. Set the interval to 0s to disable it.

The worker first captures every storage page and its versions, then scans every provider page for I3D_APPLICATION_ID and optional I3D_FLEET_ID. A failed page, invalid response or repeated cursor aborts the pass without applying that scan. It does not infer absence from an individual page.

Absence-based cleanup removes only records with known matching application/fleet ownership and older than I3D_RECONCILE_GRACE_PERIOD (default 2m). A record must be absent or no longer ALLOCATED in two consecutive complete scans, with the same storage version. Failed scans reset that confirmation. Legacy records with unknown ownership are retained when absent. Provider-visible allocated records establish scope when refreshed; applications selected with overwriteApplicationId need a separately scoped worker to reconcile their absence.

Refreshes and deletions use the version captured before the scan. Concurrent allocation, admission or update wins a conflict; reconciliation waits for a later pass instead of retrying against the newer record. Provider-only Get/List/reconciliation results are discovery information; they are not imported into session storage. Provider metadata cannot reconstruct the plugin-owned admission capacity. Successful Create persistence establishes that state, and a lost persistence result cannot be recovered from provider discovery alone. Confirmed failed allocations still use the allocation cleanup path. Update requires an existing session and cannot import a provider-only allocation.

Refreshes of the same provider generation preserve local capacity and admissions. When List observes a newer provider creation timestamp, it marks the previous record STALE in the page transaction, retaining its allocation identity and ownership for cleanup. Join and delayed Update reject that invalidated record. Repeated discovery does not rewrite it or postpone cleanup. Get and reconciliation conditionally retire the observed invalidated or older record when a replacement generation is present; this is distinct from absence-based cleanup. Older Get/List/reconciliation responses do not roll back a newer local generation.

This is eventual consistency, not proof that a server has terminated. Two complete scans plus the grace period reduce false absence but cannot eliminate a provider outage that returns successful, incomplete results. Tune the grace period to the fleet's observed propagation delay, or disable absence reconciliation when that assumption cannot be met. Multiple Nakama nodes are safe through conditional storage operations; they may perform redundant scans.

Reconciliation only repairs Nakama storage. It never calls the provider restart operation. The public Delete/lifecycle RPC remains the explicit request to restart a game server.

Get also captures the cache version before its provider request; conflicts restart the entire read up to four attempts. Delete captures the version before restarting and never removes a replacement allocation. If a join or refresh changes only the storage version, cleanup makes up to five attempts, retrying only after proving the allocation generation is unchanged; the provider restart is performed once. Legacy records without a generation cannot be retried safely. Provider-backed List pages refresh existing cached records in one storage transaction, with the entire page re-read on version conflicts. Unknown instances remain visible in the returned page without creating storage records. Nakama 3.41 returns a plain error for conditional-delete conflicts: the adapter confirms a changed/missing version with a new storage read instead of depending on an error string or write-only sentinel.

Storage pagination itself is not a transaction-wide snapshot. Records whose allocation time or storage update timestamp is at or after the pass start minus I3D_RECONCILE_CLOCK_SKEW (default 5s, minimum 1s) are excluded from refresh and absence cleanup, even if a later storage page includes them. This prevents a stale provider generation from overwriting a new allocation read during the same scan.

The clock-skew window must cover the maximum relative clock difference among allocation writers, the database and reconciliation nodes, plus timestamp precision. A simulated seven-second skew is covered by a configured ten-second window. This is a bounded-skew assumption: maintain synchronized clocks and increase the window when required; timestamps alone cannot protect against unbounded drift. Recently updated records wait for a later pass.
