# Compatibility and migration

The tested candidate supports exactly Nakama 3.41.0, nakama-common 1.48.0, Go 1.27.1 and protobuf 1.36.12. The Dockerfile pins the matching runtime and pluginbuilder image index digests. Build with that pluginbuilder; a plugin compiled with another Go toolchain or shared dependency version may fail to load.

The legacy source at f26ac9d83ebb1a70f492db70b69eacf842403cb6 pins Nakama 3.26.0/common 1.36.0. Heroic Labs reported successful use with 3.26.x. That is separate from the new candidate; no broader compatibility range is promised.

Use the root import github.com/i3dnet/nakama-i3d (package fleetmanager) and github.com/i3dnet/nakama-i3d/config. Create now returns (map[string]string, error). The first value is currently nil; connection information arrives asynchronously in the callback.

Create rejects canceled calls and invalid capacity/user lists before registering a callback. Accepted allocations retain context values but survive normal matchmaker-hook cancellation. The provider allocation stage has a 120-second default deadline (I3D_ALLOCATION_TIMEOUT). Persistence gets a fresh 30-second default budget (I3D_ALLOCATION_FINALIZE_TIMEOUT). Both stages observe graceful shutdown, and a published result wins over simultaneous deadline expiry. Set shutdown_grace_sec above the finalization budget with a margin (the examples use 45 seconds for the default 30-second cleanup budget) so Nakama can finish shutdown hooks. The container/service stop deadline must be longer still; repository Compose files allow 60 seconds. Success is reported only after storage succeeds. If a confirmed allocation fails, arrives after timeout, or cannot be persisted, the callback reports one error and the owner of that result attempts one best-effort restart with a fresh finalization budget. Cleanup failures are logged without changing the callback outcome. Ambiguous responses without a confirmed allocation ID cannot be safely restarted. A dependency that ignores cancellation is reclaimed when its known result eventually returns, while the process is alive; cache cleanup remains conditional reconciliation rather than a blind delete.

Each accepted callback receives one terminal outcome while this process remains running. Error outcomes carry nil instance, sessions and metadata. Calls without users return nil sessions. Callbacks are local and are not durable across process restart; they do not route between nodes. The example sends notifications using a separate bounded context.

Validation on 2026-09-22: root and example race tests and vet pass; scripts/check-plugin.sh built and loaded the Linux ARM64 plugin in the exact runtime with disposable PostgreSQL. The CI plugin job repeats build/load on Linux AMD64. The full lifecycle smoke also passes on both architectures, including native storage concurrency/index pagination and HTTP-authenticated lifecycle payloads. Live i3D staging remains a separate release gate.

Lifecycle RPCs update_instance_info and delete_instance_info require trusted server HTTP-key authentication. Player-session calls return PERMISSION_DENIED before payload processing. Nakama validates the HTTP key; the adapter's user-context check is not a standalone authentication mechanism. Configure a private runtime.http_key for the headless servers and verify existing callers before deploying this migration. The RPC names and player_count field are unchanged. Malformed payloads, unknown fields, empty IDs, negative or over-capacity counts and plugin-owned metadata return INVALID_ARGUMENT. Direct internal Go Update/Delete calls remain supported.

FilterBuilder.Query now returns a raw expression with quoted string values. Pass it directly through AddFiltersToMetaData; do not pre-encode it. The generated HTTP client applies URL encoding once. Internal routing keys and the i3d_ namespace are not forwarded as game metadata.

An empty FleetManager.List query reads a provider page scoped to the configured application and selects ALLOCATED entries locally because the bundled One API schema excludes status from supported filters. Always follow a nonempty cursor even if a page returns no allocated entries. A malformed provider entry fails the whole page instead of disguising an incomplete scan as complete. Nonempty List queries use Nakama's storage index. Cursors belong to their original listing mode/query/limit. Indexed sorting uses value.player_count and value.create_time.

Allocation success requires one returned ALLOCATED instance with a usable public IP and a port in 1–65535. The adapter uses One API's empty/allocate completion contract, including Arcus metadata delivery; it does not add a separate READY webhook. Live provider validation remains a staging release check.

Session storage retains the existing top-level InstanceInfo shape and adds private _i3d allocation/admission state. Provider refreshes own address, status and ordinary metadata; local capacity and admitted-player estimates survive refresh. Successful Create persistence resets local state for reused instance IDs. Provider-only Get/List/reconciliation results are not imported because the provider response cannot reconstruct admission capacity. Update now requires an existing stored session. A newer provider generation invalidates or conditionally retires the observed old record; delayed Update cannot restore an invalidated record. See [reconciliation](reconciliation.md) for discovery and cleanup behavior. Mutations use Nakama 3.41's StorageWriteRetry with five conflict retries and versioned writes; ordinary storage errors are not retried.

Join provides limited local admission accounting. Duplicate users are idempotent within the current admission epoch, and a group can be partially admitted when capacity is insufficient. Returned SessionId values are empty: these are not provider-issued reservations, do not expire after one minute, and are not game-server authentication tokens. An accepted Update player_count report updates One API, replaces the estimate and resets local deduplication; the payload does not identify individual connected players. Applications must handle reconnection, game-server validation and abandoned admissions explicitly. This adapter does not claim the full expiring-reservation contract described by Nakama's generic FleetManager interface.
